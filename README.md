# Emoji Partners

Франшиза бота-конструктора анимированных эмодзи. Партнёр приносит токен
своего бота — сервис поднимает для него отдельную копию движка
(`StickerEmojiBot`) со своей папкой данных, следит за процессом и
показывает в кабинете, что этот бот наработал.

```
партнёр ──► кабинет франшизы ──► supervisor ──► процесс движка (бот партнёра)
                   ▲                                      │
                   └────────── сводка продаж ◄────────────┘
                        (чтение базы бота, только на чтение)
```

## Что уже работает

- **Кабинет партнёра**: уровень, комиссия, оборот, клиенты, заказы,
  рефералы. Навигация — одним сообщением, которое перерисовывается.
- **Подключение бота по токену**: проверка через Telegram, отдельная
  рабочая папка, запуск, автозапуск при старте сервиса. Сообщение с
  токеном удаляется из переписки сразу.
- **Управление ботом**: запуск, остановка, перезапуск, автозапуск,
  обновление статистики, отключение с подтверждением.
- **Присмотр за процессами**: упавший бот поднимается сам, после трёх
  подряд падений остаётся лежать с внятной причиной из лога.
- **Сводка продаж** из баз дочерних ботов — раз в `STATS_INTERVAL`.
- **Уровни лояльности**: комиссия падает с ростом оборота, подписка
  снижает её ещё на `SUB_DISCOUNT`.
- **Рефералы**: ссылка `?start=r<id>`, пригласивший закрепляется навсегда.
- **Админка сервиса** (`/admin`): партнёры, боты, журнал, пересчёт
  статистики, рассылка (`/cast`).

## Чего ещё нет

**Денежной части.** Выплаты, удержание комиссии и приём оплаты за
подписку не подключены — по решению отложены на следующий шаг. Сейчас
звёзды клиентов остаются на счёте бота партнёра, а сервис считает
оборот и комиссию «на бумаге»: в кабинете это написано прямым текстом,
партнёр не введён в заблуждение.

Когда дойдём до денег, понадобится одно изменение в движке: таблица
платежей. Сейчас он журналирует заказы, но не пополнения баланса,
поэтому оплату звёздами не отличить от списания с внутреннего баланса —
а комиссию считать нужно именно с первой.

## Запуск

```bash
pip install -r requirements.txt
copy .env.example .env
python main.py
```

В `.env` обязательны `BOT_TOKEN` (бот франшизы) и `ADMIN_IDS`.

Движок едет в репозитории папкой `engine/` — на хостинге он оказывается
в том же контейнере, ставить его отдельно не нужно: его зависимости
(Pillow, fonttools, rlottie-python, svgelements) уже в общем
`requirements.txt`. Локально, если рядом лежит папка `StickerEmojiBot`
с более свежим кодом, можно указать её в `ENGINE_DIR`.

### На Bothost

Деплой из репозитория, команда запуска `python main.py` — сборщик
подставляет её сам. Две вещи, о которых стоит знать:

**Память.** Каждый бот партнёра — отдельный процесс на 150–250 МБ.
Поэтому `MAX_RUNNING=3` по умолчанию: сверх предела бот честно не
запускается и говорит об этом, вместо того чтобы уронить по памяти
весь контейнер разом. Для десятков партнёров нужен свой сервер.

**Данные.** `DATA_DIR` контейнер задаёт сам (`/app/data`), и франшиза
его слушает — но если хостинг не хранит эту папку между
передеплоями, при обновлении кода пропадут токены партнёров и их
статистика. Перед первым живым партнёром убедитесь, что папка
переживает передеплой (постоянный том или отдельная база), иначе
ботов придётся подключать заново.

Проверить сборку без Telegram и без токенов:

```bash
python selfcheck.py
```

Скрипт заводит временную базу, подключает бота с заведомо негодным
токеном, реально запускает движок отдельным процессом и убеждается, что
падение объяснено человеческим языком; затем читает продажи из базы
такого же вида, какую заводит движок. Ничего настоящего не трогает.

Посмотреть карточки всех экранов:

```bash
python preview.py
```

## Файлы

## Как это устроено

**Почему дочерний бот — отдельный процесс.** Движок написан как
самостоятельное приложение с глобальным `config`, двум токенам в одном
процессе там не разойтись. Отдельный процесс заодно означает, что
падение одного бота не роняет остальные и не роняет франшизу.

**Почему движок не пришлось править.** Он настраивается переменными
окружения, а `load_dotenv` не перетирает уже заданные переменные —
значит, окружение, переданное супервизором, сильнее его собственного
`.env`. Каждому боту уходят свой `BOT_TOKEN`, свой `DATA_DIR`, список
админов (владелец + админы сервиса) и пустой `REQUIRED_CHANNEL`, чтобы
боты партнёров не гнали аудиторию в чужой канал.

**Почему запуск ждёт строку в логе.** Живой процесс — ещё не
работающий бот: отозванный токен движок обнаруживает через несколько
секунд, уже после импортов. Поэтому супервизор ждёт до
`START_TIMEOUT` одного из двух: процесс умер (тогда партнёру
показывается строка ошибки из лога) или бот представился Telegram.

**Токены партнёров** лежат в базе в открытом виде — иначе их нечем
запускать. Файл базы в `DATA_DIR` — самое ценное, что есть у сервиса:
держите его на постоянном томе и никогда не кладите в репозиторий.
